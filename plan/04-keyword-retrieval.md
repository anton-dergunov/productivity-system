# Stage 4 — Keyword & Structured Retrieval (as Commands and as Tools)

> Goal: make exact and structured retrieval first-class — both as interactive Emacs commands and
> as tools the LLM can call — so the agent answers "where did I write X / list all Y" by *searching*
> rather than by ingesting whole files. This is the cheap half of category **E**, and it is the
> retrieval substrate that keeps later LLM context small.

**Question categories:** **E** (exact + structured); feeds **C/D/F/H/I** in Stage 5.
**Depends on:** Stage [00](00-foundations.md); pairs with Stage [03](03-org-tool-layer.md) tool wiring.
**Effort:** ~3–5 days.

---

## 4.1 Why before semantic search

At your corpus size, ripgrep + org-ql answer the large majority of "find/aggregate" queries with
zero latency, zero cost, and perfect recall on exact terms. The honest rule from your research:
*don't build embeddings until keyword search has measurably failed real queries.* This stage is
that baseline — and it doubles as the retrieval tool the agent calls so it doesn't blindly stuff
whole files into context.

## 4.4 Commands

```elisp
(defun orgllm-search-text ()      ; exact/regex across plans
  (interactive) (consult-ripgrep orgllm-plans-directory))

(defun orgllm-search-books ()     ; all :book: items
  (interactive) (org-ql-search (org-agenda-files) '(tags "book")))

(defun orgllm-search-deadlines (&optional days)
  (interactive "p")
  (org-ql-search (org-agenda-files) `(deadline :to ,(or days 14))))

(defun orgllm-search-stale (&optional days)
  "Headings with no clock/edit in DAYS and no scheduled/deadline."
  (interactive)
  (org-ql-search (org-agenda-files)
    `(and (todo) (not (scheduled)) (not (deadline))
          (not (clocked :from ,(- (or days 30)))))))
```

Add a `consult-org-ql`-style previewable jumper (steal the well-known
`my-consult-org-ql-agenda-jump` pattern) bound to e.g. `C-c l s`.

## 4.5 Retrieval as LLM tools

Expose two retrieval verbs to the agent so its answers are grounded and its context stays small:

- `org_grep(pattern)` → ripgrep hits with file:line:context (wrap `rg --json`).
- `org_query(ql_sexp)` → org-ql structured hits (heading, file, id, todo, tags, scheduled).

Plus **aggregation tools** that return tidy structured data for category-E "list everything"
questions (so the model doesn't reconstruct them from raw text):

```elisp
(defun orgllm-tool-aggregate (kind)
  "KIND ∈ books|videos|deadlines|priority-a|stale|by-tag → structured list.")
```

Pattern: the agent calls `org_query`/`org_grep`/`org_aggregate`, gets compact structured results,
then reads only the specific nodes it needs via `orgllm-tool-get-node` (Stage 3). This
**retrieve-then-read** loop is the core efficiency trick that makes Stage 5 workflows cheap.

## 4.6 Optional / alternative implementations (research)

- **Hybrid pre-ranking:** when a query is fuzzy, run ripgrep with several query expansions
  (synonyms generated by a cheap model) and union the hits — a poor-man's semantic search with no
  index. Measure how far this gets you before committing to embeddings (Stage 6).
- **`org-ql` views as saved "reports":** persist common queries (stale, no-next-action, orphan
  goals) as named views; later, Stage 5 hygiene/prioritization workflows consume these directly.
- **BM25 over org chunks** (light IR): if you want ranked keyword retrieval without embeddings,
  build a tiny BM25 index over Stage-6 chunks. This is a nice IR-flavored experiment and a strong
  baseline to compare embeddings against in Stage 9 (does semantic actually beat BM25 on your
  queries?).

---

## 4.7 Python? — No.

ripgrep + org-ql + consult are mature and elisp-drivable. (A BM25 baseline, if you do it, is also
fine in elisp at this scale, or trivially in Python if you prefer `rank_bm25` — but it's optional.)

## 4.8 Evaluation for this stage (DS)

Build `eval/datasets/retrieval.jsonl`: 30–50 real queries you'd actually ask ("where did I note
pose detection?", "all books about the back", "deadlines this month"), each with hand-labeled
**relevant node ids** (gold set). Then:

- **Recall@k / MRR / nDCG** for `org_grep` and `org_query` against the gold set.
- Tag each query as *exact* (keyword should nail it) vs *fuzzy* (vocabulary mismatch — likely a
  keyword miss). The fuzzy misses are precisely the queries that justify Stage 6; you now have a
  **measured threshold** for when to build embeddings (e.g. "keyword recall@5 < 0.7 on ≥5 fuzzy
  queries").

This dataset is reused as the retrieval benchmark in Stage 6 (semantic) and Stage 9.

## 4.10 Risks / notes

- **org-ql performance** is fine at your scale; if it ever lags, persist agenda files and use
  `org-ql-cache`.
- Don't let the agent default to "read the whole file" — bias it (in `AGENTS.md` and tool
  descriptions) toward search-then-read; verify via the audit log that it actually uses the tools.
